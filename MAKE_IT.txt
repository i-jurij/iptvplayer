## Шаг 5. `EPGManager.cpp` — новый этап «ЭТАП 2b»

Вставить **между** блоком exact-name (ЭТАП 2) и блоком построения candidates (ЭТАП 3). Логика: ищем точное совпадение `playlistNorm.baseName` с `epg.normalizedId`, с тем же region-гейтом, что и у exact-name.

```cpp
// ========================================================================
// ЭТАП 2b: Exact name ↔ normalized id
// ========================================================================
{
    std::lock_guard<std::mutex> cacheLock(m_normalizedCacheMutex);
    const NormalizedChannel *singleMatch = nullptr;
    int matchCount = 0;
    for (const auto &epg : m_normalizedCache) {
        if (epg.normalizedId.empty())
            continue;
        if (epg.normalizedId != playlistNorm.baseName)
            continue;
        bool regionOk = true;
        if (!playlistNorm.region.empty() && !epg.region.empty() &&
            playlistNorm.region != epg.region)
            regionOk = false;
        if (!regionOk)
            continue;
        singleMatch = &epg;
        if (++matchCount > 1)
            break;
    }
    if (matchCount == 1) {
        result.channelId = singleMatch->id;
        result.method = "name_to_id";
        result.score = 95;
        result.confidence = "high";
        LOG_DEBUG("FindBestMatch: NAME-TO-ID MATCH -> epgId='%s'",
                  result.channelId.c_str());
        return result;
    }
    // 0 или >1 совпадений — просто идём дальше.
    // При >1 кандидаты попадут в общий пул на ЭТАПЕ 3
    // и будут соревноваться через substring/tokens/Jaro.
}
```

Score 95 — чуть ниже `exact_name` (100), но заметно выше token/Jaro. Confidence — `high`.

**Почему при matchCount > 1 ничего не делаем специально:** на следующем этапе эти каналы всё равно попадут в `candidates` (region-гейт для них уже пройден), и их `normalizedId`/`idTokens` будут участвовать в общих подсчётах. Отдельная ветка не нужна.

## Шаг 6. `EPGManager.cpp` — этап substring (ЭТАП 4)

Сейчас проверка идёт только против `cand.baseName`. Обернуть проверку в лямбду и вызывать дважды:

```cpp
auto trySubstring = [&](const std::string &candName) -> bool {
    if (candName.empty())
        return false;
    const std::string &shortName =
        (playlistNorm.baseName.length() <= candName.length())
            ? playlistNorm.baseName : candName;
    const std::string &longName =
        (playlistNorm.baseName.length() > candName.length())
            ? playlistNorm.baseName : candName;
    if (shortName.length() < (size_t)m_substringMinLen)
        return false;
    if (longName.find(shortName) == std::string::npos)
        return false;
    for (const auto &sw : m_stopwords)
        if (shortName == sw)
            return false;
    return true;
};

for (auto &cand : candidates) {
    bool nameSub = trySubstring(cand.baseName);
    bool idSub = trySubstring(cand.normalizedId);
    if (nameSub || idSub) {
        cand.score = 75;
        cand.fromSubstring = true;
        cand.fromId = idSub && !nameSub;  // приоритет за именем
    }
}
```

Оригинальный цикл со всем содержимым заменяется этим блоком. Логика существующих проверок сохранена один в один.

## Шаг 7. `EPGManager.cpp` — этап token-sort (ЭТАП 5)

Сейчас ratio считается для одной пары токенов. Вынести подсчёт в лямбду и вызвать дважды:

```cpp
auto computeTokenRatio = [&](const std::vector<std::string> &t2) -> double {
    const auto &t1 = playlistNorm.tokens;
    if (t1.empty() || t2.empty())
        return 0.0;
    std::unordered_set<std::string> set1(t1.begin(), t1.end());
    std::unordered_set<std::string> set2(t2.begin(), t2.end());
    size_t inter = 0;
    for (const auto &t : set1)
        if (set2.find(t) != set2.end())
            inter++;
    size_t uni = set1.size() + set2.size() - inter;
    double r = (uni > 0) ? static_cast<double>(inter) / uni : 0.0;
    // Строгое подмножество — как раньше
    if (set1 != set2 && inter == std::min(set1.size(), set2.size()))
        r = 0.0;
    return r;
};

for (auto &cand : candidates) {
    double r1 = computeTokenRatio(cand.tokens);
    double r2 = computeTokenRatio(cand.idTokens);
    bool fromId = (r2 > r1);
    cand.ratio = std::max(r1, r2);

    if (cand.ratio >= m_tokenHigh) {
        cand.score = 85;
        cand.fromId = fromId;
        LOG_DEBUG("FindBestMatch: token-high candidate '%s' (ratio=%.2f, id=%d)",
                  cand.baseName.c_str(), cand.ratio, (int)fromId);
    } else if (cand.ratio >= m_tokenLow) {
        cand.score = 65;
        cand.fromId = fromId;
        LOG_DEBUG("FindBestMatch: token-low candidate '%s' (ratio=%.2f, id=%d)",
                  cand.baseName.c_str(), cand.ratio, (int)fromId);
    } else {
        cand.score = 0;
        // fromId не трогаем — кандидат дальше не пойдёт,
        // его флаг больше нигде не читается.
    }
}
```

Существующее правило strict-subset сохранено, `fromSubstring` больше не используется — можно его убрать из Candidate (не критично, но для чистоты).

## Шаг 8. `EPGManager.cpp` — этап Jaro-Winkler (ЭТАП 6)

Считаем Jaro против обоих полей, берём max по значению и обновляем флаг `fromId`, если id дал строго больше:

```cpp
for (auto &cand : candidates) {
    if (cand.score == 0)
        continue;
    if (cand.score == 85) {
        // без изменений, высокий score не трогаем
    } else {
        double jaro1 = ComputeJaroWinkler(playlistNorm.baseName, cand.baseName);
        double jaro2 = cand.normalizedId.empty()
                           ? 0.0
                           : ComputeJaroWinkler(playlistNorm.baseName,
                                                cand.normalizedId);
        double jaro = std::max(jaro1, jaro2);

        if (jaro2 > jaro1)
            cand.fromId = true;
        else if (jaro1 > jaro2)
            cand.fromId = false;
        // если равны — оставляем то, что выставил token-этап

        LOG_DEBUG("FindBestMatch: Jaro-Winkler for '%s' = %.4f (id=%.4f)",
                  cand.baseName.c_str(), jaro1, jaro2);

        if (jaro >= m_jaroHigh)
            cand.score += 5;
        else if (jaro >= m_jaroMedium)
            cand.score += 3;
        else if (jaro < m_jaroLow)
            cand.score -= 5;
        if (cand.score > 100) cand.score = 100;
        if (cand.score < 0)   cand.score = 0;
    }

    // Бонусы за качество/регион — без изменений
    if (cand.score > 0) {
        if (!playlistNorm.quality.empty() && !cand.quality.empty() &&
            playlistNorm.quality == cand.quality)
            cand.score += 2;
        if (!playlistNorm.region.empty() && !cand.region.empty() &&
            playlistNorm.region == cand.region)
            cand.score += 2;
        if (cand.score > 100) cand.score = 100;
    }
}
```

## Проверка после реализации

1. **iptvorg-кейс.** Плейлист `Match TV HD`, tvgId пустой. EPG: id=`match-tv`, displayName=`Матч ТВ`. Ожидание: `method=name_to_id`, score=95.
2. **Ambiguous.** Плейлист `TNT`. EPG: id=`tnt` (displayName `ТНТ`) и id=`tnt.us` (displayName `TNT USA`). Ожидание: exact-name не срабатывает, exact name↔id даёт 2 совпадения → fall-through в пул, оба кандидата соревнуются по token/Jaro.
3. **Регрессия exact-name.** Плейлист `BBC One`, EPG displayName=`BBC One`. Ожидание: `method=exact_name`, score=100 (этап 2b не должен перехватывать раньше).
4. **Регрессия tvg-id.** Плейлист tvgId=`bbc1`, EPG id=`bbc1`. Ожидание: `method=tvg-id-direct`, score=100.
5. **Фильтр id.** EPG id=`hd`, `24`, `1tv`. Ожидание: `hd` (len<3) и `24` (нет букв) — не участвуют, `1tv` — участвует.
6. **Совместимость.** Каналы, которые матчились до изменений, должны матчиться теми же method и score, если id-путь не дал более сильного совпадения. Регресс по существующим логам матчинга.

Xtream Codes API:
Протокол предоставляет структурированный доступ к контенту, что гораздо удобнее, чем простой плейлист. 
Основные возможности:
  Аутентификация и информация об аккаунте: Плеер может проверить статус подписки, дату её окончания 
    и лимит одновременных подключений

. Категории (Category Management): Каналы, фильмы и сериалы организованы по категориям 
(например, «Спорт», «Кино», «Новости»), что упрощает навигацию

. Живые трансляции (Live Streams): Доступ к списку ТВ-каналов и возможность их воспроизведения

. VOD и Сериалы (Video on Demand & Series): Доступ к библиотеке фильмов и сериалов, 
включая информацию о конкретном фильме или эпизоде

. EPG (Телепрограмма): Получение данных электронного телегида для каналов

. Catchup/Timeshift: Возможность просмотра архива передач за прошедшие дни

📱 Типовые экраны настройки Xtream Codes

1. Экран добавления провайдера (Provider Setup)
Это первый экран, который видит пользователь при попытке добавить новый источник контента. Обычно он содержит:

    Переключатель типа подключения: M3U, Xtream Codes, Stalker Portal.

    Поля ввода: Server URL (адрес), Username (логин), Password (пароль).

    Кнопка «Connect» или «Login».

2. Экран выбора контента (Content Hub)
После успешного подключения открывается главный экран, где контент автоматически группируется:

    Live TV: список каналов, сгруппированный по категориям (Спорт, Новости, Кино).

    Movies (VOD): библиотека фильмов с постерами.

    Series: список сериалов с сезонами и эпизодами.

    Radio: если провайдер предоставляет радиоканалы.

3. Экран категорий и списка каналов

    Слева или сверху: список категорий (например, «Все», «Спорт», «Детские»).

    Справа или снизу: список каналов с логотипами и названиями.

4. Экран EPG (телепрограммы)

    Сетка вещания: время по горизонтали, каналы по вертикали.

    Текущая передача: подсвечена, с прогресс-баром.

    Описание: всплывающая подсказка или нижняя панель с информацией о программе.

## Чего не хватает под Xtream Codes

### 1. Управление провайдерами (провайдер как сущность)

Сейчас `Playlist` — это плоский список каналов. Xtream — это **аккаунт с credentials**, у которого есть:
- статус подписки (`auth`, `status`, `exp_date`, `is_trial`);
- лимит одновременных подключений;
- сервер, username, password;
- динамический URL (провайдер может менять домен).

**Чего нет:**
- Диалога «Add provider» с полями `Server`, `Username`, `Password`.
- Модели `XtreamAccount` (отдельно от `Playlist`).
- Проверки credentials при добавлении (`player_api.php` → `user_info`).
- Отображения статуса подписки в UI (можно в статусбар слот 1 или в панель Playlists).

**Что переиспользуется:**
- Диалог добавления URL-плейлиста (`AddPlaylistUrlDialog`) — по структуре почти 1-в-1, меняются только поля.
- Паттерн `EVT_ADD_FROM_URL_SUCCESS` / `ERROR` для асинхронной проверки credentials.
- `updateStatusBar`, `HighlightLoadedPlaylistInList`.

### 2. Контент-хаб вместо плоского списка каналов

Сейчас `m_allChannels` — один список. У Xtream — **четыре корзины**:

| Корзина | API-эндпоинт | Формат |
|---|---|---|
| Live | `get_live_streams` | потоки |
| VOD (фильмы) | `get_vod_streams` | фильмы |
| Series | `get_series` | сериалы (с сезонами/эпизодами) |
| Radio | `get_live_streams` (type=radio) | аудио |

**Чего нет:**
- Страницы `Movies` и `Series` в notebook.
- Кнопок `Movies`, `Series` в header.
- Второго уровня навигации (категория → список контента).
- Постеров/обложек (как в ChannelCards, только для VOD).

**Что переиспользуется:**
- `ChannelCards` / `ChannelList` — почти как есть. Меняются только поля карточки (постер вместо логотипа, год/жанр вместо группы).
- `wxSimplebook` (`m_channelViewBook`) — grid/list переключение 1-в-1.
- Filters panel (`m_groupChoice`, `m_sortChoice`) — можно переиспользовать как «Категория» + «Сортировка».
- `createChannelsView()` — паттерн создания страницы.

### 3. Сериалы (глубина в 2 уровня)

Сейчас нигде нет двухуровневой навигации. У сериалов: сериал → сезоны → эпизоды.

**Чего нет:**
- Модели `SeriesInfo`, `SeasonInfo`, `EpisodeInfo`.
- Экрана сериала (обложка + описание + список сезонов).
- Списка эпизодов сезона.

**Что переиспользуется:**
- `EPGPanel` как образец «детального» экрана — можно взять его структуру для карточки сериала.

### 4. EPG от провайдера

Сейчас EPG идёт через `EPGManager` (свои источники). Xtream даёт EPG через `xmltv.php` или `get_short_epg`.

**Чего нет:**
- Импорта EPG по credentials провайдера.
- Catchup / Timeshift — воспроизведения архива.

**Что переиспользуется:**

### 5. Поиск

Сейчас поиска нет нигде.

**Чего нет:**
- Поля поиска (в header или в каждой странице).
- Кросс-поиска по Live + VOD + Series.

**Что переиспользуется:**

### 6. VOD-специфика в плеере

`VideoPanel` заточен под live: temp playlist, EOF-детект для переключения канала. Для VOD нужны:
- Сохранение позиции (resume from where left off).
- Отображение оставшегося времени (уже есть в `m_timeRemainingLabel`).
- Кнопки «Play from beginning» / «Resume».

**Что переиспользуется:**
- Почти всё. `m_tempPlaylist`, `PlayPrev/Next`, `m_eofTimer`.
- `ProgressInfo::duration` уже работает, `m_isLiveStream` уже детектит live vs VOD — надо просто добавить сохранение позиции в конфиг.
